# Parallel context graph-build audit

## Verdict

There is a plausible, narrow CPU parallelism opportunity between **different** `llama_context` objects, because `llama_model::build_graph()` builds into the result object's own GGML context and graph. The current Meta replay guard is broader than that call: on a graph rebuild, `process_ubatch()` acquires it before result/scheduler reset, holds it through `model.build_graph()`, scheduler allocation, input population, and `graph_compute()`, then unlocks. A guard split could let independent CPU graph construction overlap.

This is **not yet safe as a general-purpose env switch**. `build_graph()` has shared callback/plug-in entry points with mutation or thread-safety that is not guaranteed, and the current code has no per-`llama_context` decode mutex. Meta's owner and collective paths also rely on a specific global-to-owner/cohort lock order. In addition, Meta weight-view `init_tensor` deliberately reacquires the global replay guard, so graph allocation would remain serialized for those views even if graph construction became concurrent.

The lowest-risk candidate is a default-off mode that releases the global guard only around the pure `model.build_graph()` interval, after synchronizing and resetting the calling context, and reacquires it before scheduler allocation. Keep all existing behavior by default. Before enabling the candidate, gate or isolate samplers, user callbacks, Qwen4Exp HC plug-in initialization, and shared-memory target/draft contexts. The likely gain is limited to the `t_build` portion; this audit does not estimate throughput.

## Current guard and context ownership

- In [`llama-context.cpp`](../src/src/llama-context.cpp), `guard_meta_build` is true when Meta replay guarding is enabled and the context has a Meta backend (3180–3181). On rebuild, the code first drains tensor-split work, locks the replay guard, resets the result/scheduler, builds the model graph, allocates it, populates inputs, and computes it; the lock is released after `graph_compute()` (3258–3272, 3287–3303, 3325–3346, 3351–3362). Graph reuse generally avoids this lock when the graph is already replay-ready; a not-ready graph takes it at 3245–3247.
- `llama_model::build_graph()` creates a temporary architecture graph builder and returns its graph ( [`llama-model.cpp`](../src/src/llama-model.cpp:3362)). `llm_graph_context` binds `ctx0` and `gf` to `params.res` ( [`llama-graph.cpp`](../src/src/llama-graph.cpp:1868)); each `llm_graph_result::reset()` creates its own `ggml_context` and graph in `ctx_compute` (1660–1698). Each `llama_context` also constructs its own backend instances/scheduler and stores its own `moe_cache` and `ft_moe` ( [`llama-context.cpp`](../src/src/llama-context.cpp:927), [header](../src/src/llama-context.h:535)). The model weights/architecture parameters are read as shared model state during normal graph construction.
- `llama_context::decode()` has no internal mutex, and no mutex member or lock around `decode()`/`process_ubatch()` exists in the inspected context source/header. The public caller must currently serialize mutation of one context. A context-local graph mutex alone would not make concurrent `decode()` calls safe because batch allocation, output accounting, memory preparation, sampling, and graph-result slots are all mutated outside the graph builder.
- `ggml_graph_next_uid()` uses an atomic counter in `ggml.c:58–70`; graph UID allocation is not a shared-map race.

## Shared mutable state reachable from graph construction

1. **Sampler backend hooks are stateful.** `llm_graph_context::build_sampling()` calls each sampler's `backend_reset()` and `backend_apply()` while assembling the graph ( [`llama-graph.cpp`](../src/src/llama-graph.cpp:4470–4529)). The `samplers` map is copied, but its values are raw `llama_sampler *` pointers. If two contexts reference the same sampler object, these callbacks can race. The general feature must require no backend samplers, or require distinct sampler instances / a documented thread-safe sampler contract. The same applies to custom graph callbacks passed in `llm_graph_params::cb`.

2. **Qwen4Exp HC uses a process-global owner registry.** `qwen4exp_hc_owner()` keeps a static map keyed by backend device and a mutex around owner creation/lookup; the opaque owner is then used by `build_hc()` / `build_hc_combine()` outside that mutex ( [`qwen4exp.cpp`](../src/src/models/qwen4exp.cpp:318–355, 399–403, 464–468)). The installed FreeToken dense implementation's HC build functions only create per-graph custom GGML nodes with that owner as userdata, so those calls appear read-only. However, `qwen4exp_hc_api` is a non-atomic global pointer written while new per-device owners are created and read after the owner mutex is released. Concurrent *first* graph builds on different devices can therefore race on its publication. Gate graph-build parallelism off when `LLAMA_QWEN4EXP_HC_FUSION` is enabled until the pointer is published once/atomically or all device owners are prewarmed. The debug-only QSA shape/demotion registries are mutex-protected; static env values are function-local immutable values.

3. **The MoE expert cache is per-context, but not internally synchronized.** Each context creates its own `llama_moe_cache` (`llama-context.cpp:1064–1082`; `llama-context.h:537–539`). Graph construction performs `find()` and writes the current routing node through `note_ids()` (`llama-graph.cpp:1992, 2021–2026`). This is safe between distinct contexts when each owns a distinct cache, but concurrent calls on the same context/cache remain unsafe. Do not infer that all context state is protected by the Meta guard.

4. **Target/draft memory may share KV storage.** Context creation passes `ctx_other` memory through `mem_other` (`llama-context.cpp:1000–1010`); `llama_kv_cache` stores the other cache and can share its cell implementation (`llama-kv-cache.cpp:80–100`). A graph-only parallel window is viable only after each batch's memory context is fully prepared and frozen, and must not overlap cache apply/compute or cache reset. This is especially relevant when the target/MTP contexts share memory.

5. **Adapters and backend plug-ins are borrowed pointers.** `llm_graph_context` receives `ft_moe`, cvec, LoRA, memory, cross-attention, samplers, and callback pointers from the calling context. The LoRA lookup itself is a map read; its object still must outlive the build and must not be concurrently mutated/freed. The FreeToken dense/MoE owner is context-owned (MTP cloning creates a separate owner/scratch), but graph-build plug-in calls should be included in any thread-safety gate rather than assumed safe from the GGML graph being local.

## Meta owner/cache and lock order

- With `GGML_META_CONTEXT_VIEWS=1`, shared WEIGHTS buffers have a shared external-view binding directory guarded by its mutex; each scheduler epoch has a separate owner token and owner-local descriptor arenas/split cache guarded by owner mutexes (`ggml-backend-meta.cpp:637–705`, `ggml-meta-context-owner-private.h:48–88`). `bind_external_weight_view()` uses directory-then-owner order; owner unbind releases the owner lock before acquiring directories (`ggml-backend-meta.cpp:1018–1058, 937–969`). These are the cross-context registries most directly touched by allocation.
- Once a Meta WEIGHTS buffer is marked WEIGHTS with context views enabled, `set_usage()` resolves both split-state cache modes and freezes the static cache (`ggml-backend-meta.cpp:3164–3182`). A cache miss for a frozen static tensor aborts instead of mutating the cache (`ggml-backend-meta.cpp:2198`). `ggml_backend_meta_buffer_context_needs_shared_guard()` avoids the global guard for frozen WEIGHTS only when replay-guard tracing is off (1106–1116); compute buffers remain context-local. External weight views use owner-local split-state containers.
- Dynamic shared WEIGHTS-view initialization still forces the global replay guard: `ggml_backend_meta_buffer_init_tensor()` creates `ggml_meta_owner_lock_scope(true)` before owner locking and recursive descriptor materialization (`ggml-backend-meta.cpp:2736–2745`). The private helper documents global-replay-guard-before-owner lock ordering (`ggml-meta-owner-lock-order-private.h:6–19`). Therefore changing only the `llama_context` lock cannot make graph allocation fully concurrent; the current Meta view setup can still serialize that portion.
- Meta graph compute deliberately supports concurrent ready contexts but imposes cold-path and collective ordering. It checks `ready_at_entry`, takes the replay guard for cold/rebuild work, then takes sorted per-physical-device submit-order locks only through enqueue (`ggml-backend-meta.cpp:5393–5417`; [`ggml-meta-submit-order-private.h`](../src/ggml/src/ggml-meta-submit-order-private.h:10–39)). Keep `replay guard -> owner/cohort locks` order. The V48/V49 lockstep changes make the cold path retain the replay guard while device locks are held; do not reintroduce a guard-suspend/rank-lock inversion.
- `ggml_backend_sched_reset()` unbinds only the active owner epoch and drains first if `all_work_drained` is false ( [`ggml-backend.cpp`](../src/ggml/src/ggml-backend.cpp:3626–3647)). The surrounding rebuild path explicitly synchronizes tensor-split work before `res->reset()`/scheduler reset and has different order for cached versus uncached results (`llama-context.cpp:3258–3273`). A new lock split must keep this per-context lifetime sequence intact; never move reset outside the calling context's serialized request lifecycle.

## Recommendation

Do not globally replace `guard_meta_build` with a per-context mutex. A bounded experiment could release the replay guard only during `model.build_graph()` while preserving the current per-context request serialization and retaining the global guard around reset/owner unbind, backend allocation, and cold Meta graph preparation. This needs an explicit opt-in and default-off gates for:

- same-context concurrent `decode()` (still unsupported);
- non-empty/shared backend samplers or a custom graph callback;
- `LLAMA_QWEN4EXP_HC_FUSION=1` until first-owner API publication is race-free;
- graph building while target/draft memory is being prepared/applied;
- `GGML_META_REPLAY_GUARD_TRACE=1` or unfrozen/missing static WEIGHTS caches.

Before coding, capture separate per-context `t_build`, `t_alloc`, and `t_inputs` durations on the same phase. If `t_build` is a small fraction of the reported 1.2 s, the narrow unlock cannot materially help; the static view `init_tensor` path may continue serializing allocations anyway. No source changes, builds, or GPU runs were performed for this audit.
