# TurboPrefill context-side port map (2026-10-15)

Read-only comparison of the pinned TurboPrefill context source, the active AC922 private `llama-context.cpp`, and the existing `LLAMA_PREFILL_FRAME_PIPELINE` / `llama_memory_hybrid_idx_context::freeze_current()` path. The GGML scheduler implementation is owned by a separate review lane. No source, build, service, or GPU was changed or run here.

## Conclusion

TurboPrefill is a **logical-batch capture/replay protocol**: accumulate multiple eligible ubatches, execute split 0 as each ubatch arrives, capture the other split inputs/state, then diagonally replay the remaining scheduler splits. The private `LLAMA_PREFILL_FRAME_PIPELINE` is **per-ubatch state ownership and eligibility around ordinary scheduler execution**. It freezes the current hybrid memory view and guards async FIFO/meta replay, but it does not accumulate ubatches or call a staged scheduler API.

The directly reusable context-side pieces are the current fixed-shape/sequence eligibility discipline, `freeze_current()` memory snapshots, `res->set_params(gparams)` binding, fail-closed drain boundaries, and Turbo's deferred `h_nextn` read contract. A port needs a batch-level stage controller, one memory-frame owner per captured ubatch, and an explicit policy for every host output whose producer may be delayed. It must also map the scheduler's explicit stage plan to the existing two Meta3 islands; `n_splits` or `n_backends` cannot be assumed to mean “island A then island B”.

The Turbo source is pinned to private `sergey-automation/llama.cpp` commit `ba0d2b3918c4662d8a1fb2eee21c365265f2901f` (Aug 16, 2026), targeting upstream b10451. It is materially older than the current private v0.5-derived branch, so the context code should be treated as a behavioral reference, not a cherry-pick. Parent clarified that “nativefreeze_current” refers to the existing `freeze_current()` implementation, not a separate directory; no standalone directory by that name exists in the mirror.

## TurboPrefill context lifecycle

The fixed Turbo `llama-context.h` defines `llama_turboprefill_state` with `enabled`, signed `stage`, `ubatch_index`, `n_turbo_ubatches`, and `turbo_start_ubatch` (`src/llama-context.h:323-385` at the pinned revision). Its lifecycle is:

1. `decode()` validates one logical batch, checks the workload, and calls `begin_batch()` once (`src/llama-context.cpp:1769-1829`). Eligibility requires `TURBOPREFILL`, at least `2 * n_ubatch` tokens, a non-MTP context, no embedding pooling, causal attention, pipeline parallelism, `LLAMA_SPLIT_MODE_LAYER`, and more than one model device. If there are multiple outputs, it allows at most one output per sequence; it does not prove the output is specifically on the final token.
2. `begin_batch()` computes the number of full turbo ubatches. A remainder is standard work. If GDN/recurrent state reports `rs_z >= 0` on the first ubatch, `stage_for_ubatch()` leaves that first ubatch on the standard path and starts capture at the next one (`llama-context.cpp:1351-1376`, header `:331-382`). Positive stage IDs mean capture/defer; a negative stage marks the last captured ubatch and triggers replay. A one-ubatch “turbo” series falls back to the standard path.
3. Every ubatch still runs through the normal memory cursor: `mctx->apply()`, graph build/reuse, input binding, compute, output extraction, then `finish_ubatch()`. Context advances the memory cursor only after each ubatch is processed. `finish_batch()` resets the stage state at the end (`llama-context.cpp:1924-1927,2085-2091`).
4. The scheduler owns the capture accumulator (`saved_ubs`), not `llama_context`: stage 1 clears saved ubatches and resets its pinned arena; positive stages execute and synchronize split 0, then snapshot that ubatch and return. The final negative stage captures the last ubatch, builds packed pinned/host intermediate banks, runs diagonal replay, synchronizes, restores live scheduler metadata/split state, clears `saved_ubs`, and compacts the pinned arena (`ggml/src/ggml-backend.cpp:3155-3336`). The saved descriptor carries split graph snapshots, inputs/copies, tensor metadata, input plans, live/intermediate banks, and deferred tensor-get requests (`:854-893`).
5. The current Turbo context explicitly registers `t_h_nextn` host reads for delayed replay when `stage > 0` (`llama-context.cpp:2049-2071`). The scheduler API binds the request to the producing split of the just-captured ubatch; it returns false for an invalid/non-produced tensor and handles split-0-produced data as already completed (`ggml-backend.cpp:3347-3392`).

The scheduler event arrays are cached per scheduler pointer and split count; saved ubatch data is per logical batch and released only after replay synchronization. Therefore a scheduler rebuild or error path must drain first and discard/restore the accumulated batch as a unit. `decode()` must not let a partially captured prompt be treated as a completed prefix.

## Existing native freeze/frame path

The current private context selects `LLAMA_PREFILL_FRAME_PIPELINE` only after environment, Meta replay, scheduler count, topology, memory type, batch shape, FIFO, and warmup checks (`src/llama-context.cpp:2961-3017`). It is restricted to Qwen4Exp, two Meta3 backends plus CPU, ordinary default context, one fixed full ubatch, no outputs, no embeddings, no callback, no MTP chain, no graph-reuse disable, and no MoE cache. QSA pooled multi and block-multi are rejected (`:2980-2994`). It uses the normal `graph_compute()` route; there is no Turbo stage argument or saved-ubatch replay in this context path.

For an eligible ubatch, the context applies the live memory cursor, calls `hybrid_idx->freeze_current()`, passes the frozen view through `graph_params()`, binds it with `res->set_params(gparams)`, and retains a `shared_ptr` in `prefill_frame_owner` after compute (`:3078-3098,3144-3147,3310-3332`). New-sequence, memory-update, reserve, graph-rebuild, and graph-error paths drain or reset frame state (`:2964-3017,1315-1316,1544-1585,3227-3245,3349-3372`). The policy tracks shape, FIFO/CPU-gather readiness, graph reuse, and meta replay readiness, but holds only one current owner and warmup state; it is not a queue of UBatch contexts.

`freeze_current()` is useful to Turbo because it copies the current ubatch and freezes the attention KV and recurrent contexts, plus the indexer KV context and QSA selector-cell plan. It rejects QSA-multi transactions; for a frozen frame it sets `block_pool_fast_path=false` and recomputes from the immutable cell view rather than depending on mutable pooled-block rows (`llama-memory-hybrid-idx.cpp:1675-1738`, `llama-memory-hybrid.cpp:303-326`). It is a **metadata/cursor snapshot over the existing shared state buffers**, not a copy of model KV/GDN storage and not a rollback checkpoint.

## Qwen4Exp hybrid idx/GDN/QSA and MTP interaction

- **GDN/recurrent:** Turbo already inspects generic hybrid/recurrent contexts for `rs_z` and sends the first ubatch requiring recurrent initialization through the standard path. It does not snapshot all current private `s_copy`, recurrent head, or QSA state itself. Keep the frozen per-ubatch memory context alive until the stage that consumes it has completed.
- **QSA/indexer:** `llama_memory_hybrid_idx_context` inherits the generic hybrid context, so the Turbo `dynamic_cast` can see its recurrent child, but the pinned Turbo context contains no `get_idx()`, pooled-QSA, or `freeze_current()` handling. Current private frame eligibility does inspect `get_idx()`, `blk_multi()`, and `LLAMA_QSA_POOLED_MULTI`; keep pooled multi disabled for a first port and retain one `freeze_current()` snapshot per saved ubatch. The frozen QSA cell plan points into the frozen indexer context, so owner lifetime must cover the replay.
- **Output-producing rows:** `embeddings_nextn` is permitted by Turbo's eligibility (the log explicitly records it) and its `t_h_nextn` copy is deferred via `ggml_backend_sched_turboprefill_register_tensor_get`. A dedicated MTP draft context (`ctx_type == LLAMA_CONTEXT_TYPE_MTP`) is excluded. The target context with an MTP `h_nextn` export may still be eligible if the deferred row-copy contract is preserved.
- **Native HC tap / DFlash:** `extract_layer_inputs()` copies per-layer F32 rows immediately (`src/llama-context.cpp:4412-4441`). Turbo only shows a deferral registration for `t_h_nextn`, not these native HC taps. For the first Turbo trial, reject contexts with `embeddings_layer_inp` enabled unless the same deferred-get API is extended to those tap tensors and their token offsets. Do not run DFlash target feature extraction over an uncaptured/unfinished ubatch.
- **Logits and other outputs:** Turbo permits up to one output per sequence but does not visibly defer all logits/embedding/sampler readbacks in the context source. A safe initial gate should require `n_outputs == 0` for every captured ubatch and allow the single final output only after replay completes; otherwise add a general per-ubatch deferred-output lease. Ensure output row offsets and `output_ids` reorder happen after the registered reads complete.

## Minimum context-side API and reuse points

1. Add a per-logical-batch stage state equivalent to Turbo's stage counter. Begin it only after batch eligibility is known; derive `n_turbo_ubatches` and the recurrent-init prefix from the actual memory context; pass an explicit stage plan to the scheduler at each `process_ubatch()`.
2. After `mctx->apply()`, create one `freeze_current()` owner per captured ubatch and bind it to that graph's `llm_graph_result` with `res->set_params()`. Retain all owners through final replay synchronization; a single `prefill_frame_owner` pointer is insufficient for multiple saved ubatches unless scheduler capture is proven to own every referenced context input.
3. Keep the existing `prefill_frame_policy` as a fail-closed admission/warmup gate, but extend it with an accumulated-batch state: fixed UBatch shape, sequence/position range, `n_kv`, `n_rs`, recurrent head/`rs_z`, QSA state/selector, and which outputs have been deferred. Do not conflate this context snapshot with a scheduler graph-cache entry.
4. Use a scheduler-facing `stage_compute(stage)` plus a generic `register_tensor_get(ubatch_id, tensor, dst, offset, size)` contract. The currently visible Turbo API is specialized to the latest captured ubatch and only one caller is present (`t_h_nextn`); native HC tap rows need the same ownership and offset discipline.
5. Introduce one context `finish_or_abort_batch()` path. Success: wait for final scheduler replay, make deferred host outputs visible, finalize output mapping, then release all frame owners. Failure/cancel/rebuild/sequence reuse: drain every submitted stage, invalidate the whole captured logical batch, restore or remove all affected KV/GDN/QSA state from the earliest captured position, clear the scheduler accumulator, and release owners only afterward. The current standard error cleanup is per failing ubatch and is not enough to undo earlier split-0 side effects from a multi-ubatch capture.

## AC922 two-Meta3 fit

The current frame candidate requires `!cparams.pipeline_parallel` and tensor-split two-Meta3 topology; Turbo's copied eligibility requires `pipeline_parallel` and layer split. The two modes cannot be combined by environment flags. To use Turbo's intra-prompt idea with this machine, the other lane must expose a scheduler plan where the first execution stage is CPU/PLE preparation as applicable, followed by the two Meta3 islands with explicit boundary dependencies. Context should consume that explicit stage plan rather than treating `n_backends == 3` or `n_splits == 3` as proof of CPU/A/B ordering.

The current stateful frame fixture verified exact synthetic KV/GDN state but recorded no cross-island kernel overlap; its host submit path completed B before A. That makes `freeze_current()` a correctness/lifetime reuse point, not evidence that the current context path already supplies Turbo throughput.
