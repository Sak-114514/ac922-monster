# Prefill critical-path audit (read-only)

Date: 2026-10-15. Scope: existing V11 Nsight trace, V16 log, V20/V21 launch/runtime records, and current private source. No GPU/model run and no core-source changes were made for this audit.

## Evidence and limits

- V11 trace: `results/v11-full-trace-20261015T052734Z/fullrun.sqlite`, `prefill-trace-summary.json`, run wave `four8k128-profiled`. It ran `runtime-perf-v10`, `LLAMA_ISLAND_SPLIT=3,3`, `--parallel 4`, `--ubatch-size 1024`; hybrid PLE allocation failed its per-NUMA reserve check, so the 27.5 GiB PLE table fell back to the original lazy GGUF host path. This is an older, CPU-ple-heavy runtime, not a current V20/V21 performance baseline.
- V20 runtime proof: `standard-semantic-20261014/results/20261015T113214Z/runtime-proof.json` points to `runtime-perf-v20`; target configuration is `--batch-size 8192 --ubatch-size 3072`, parallel 4, hybrid PLE. V20 loaded an 8 GiB GPU + 18.82 GiB NUMA-striped DDR PLE placement. Its step-timing log includes prefill `compute` averages of ~604 ms and ~1,135 ms per call in two 32-call windows, with `inputs` ~2.5 ms and ~13.9 ms respectively; these are graph-compute wall spans, not an isolated PLE profile. The same complete V20 server log has ten frame-policy records: two 3,072-token `shape-warmup` records and subsequent 2,048-token shape drains; no `active` record appears.
- V21 was launched and completed with `LLAMA_ISLAND_SPLIT=6` (single six-GPU Meta backend). `results/20261015T111920Z/runtime-proof.json` identifies `runtime-perf-v21`; its semantic gate is `PASS`. `benchmark-tp6v21/summary.json` uses disjoint real-token-pool 8K inputs. Measured prompt rate is PP 890.19 tok/s, single-stream common TG 32.422 tok/s, two-stream common TG 68.970 tok/s, and four-stream common TG 100.377 tok/s. Do not infer run status from the earlier stale `tp6v21-prepared.json`.

## Critical-path measurements (V11)

The prefill window is 52,449.477 ms. Summing kernel durations across GPUs is not a critical path; I merged activity intervals across devices instead.

| Activity | Wall-union time | Meaning |
|---|---:|---|
| Any GPU kernel/memcpy/memset active | 20,168 ms | 38.5% of the prefill window |
| All six GPUs with no recorded activity | 32,281 ms | 61.5%; 477 idle gaps >1 ms, 80 >10 ms; longest 2,218 ms |
| Island GPUs 0–2 kernel union | 10,003 ms | — |
| Island GPUs 3–5 kernel union | 9,421 ms | — |
| Both islands kernel-active simultaneously | 0 ms | For all GPU activities including copies, island overlap is only 146 ms |

The aggregate GPU-kernel sums are not additive wall times. Merging kernels, memcpy, and memset per island gives 10,356 ms for GPUs 0–2 and 9,959 ms for GPUs 3–5, with only 146 ms overlapping. By category, union across any GPU was: P2P all-reduce 5,889 ms, grouped MoE 5,328 ms, QSA FlashAttention 2,791 ms, NCCL 2,047 ms, and the sampled F16 CUTLASS group 1,872 ms. These intervals may overlap with each other. Even complete elimination of any single category cannot recover more than its measured union time.

Host CUDA API totals also need care: `cudaStreamSynchronize` summed to 10,947 ms across calls, but its interval union overlapped only 168 ms (0.52%) of the all-GPU-idle intervals. The API sum is therefore not the explanation for the 32.3 seconds with no GPU activity.

A V11 `step-timing` window for target context `0x10012c36e60` covered token shapes 8..1024 and reported `compute=890,951 us`, `inputs=10,002 us`, `build=4,888 us`, `alloc=23,265 us`, `total=929,402 us` per call, averaged over 32 calls. That is about 28.5 seconds of graph-compute wall time over 32 calls. It is close to the 32.3-second all-GPU-idle budget and points to synchronous host work inside `graph_compute_async`; it does not prove that all of `compute` is PLE GET_ROWS without a CPU profile.

V11 CUDA copies totaled 14.27 GiB HtoD, 14.25 GiB DtoD, and 6.24 GiB P2P. Their summed event durations were 1.321 s, 44 ms, and 201 ms respectively. These copies merit attention but do not explain the full GPU-idle span on their own.

## Source findings

1. **PLE is gathered once per ubatch, not once per PLE layer.** `src/models/qwen4exp.cpp` calls `build_inp_ple()` once before the layer loop (`:517`); it constructs the CPU hash-row input and a single `ggml_get_rows(per_layer_token_embd, rows)` (`:3242`). `llm_graph_input_ple::set_input()` computes predecessor/hash IDs synchronously and writes the row-index tensor (`:3094 onward`). `GGML_CPU_PLE_PAGE_BATCH` then sorts and groups cold rows in `ggml/src/ggml-cpu/ple-row-cache-api.h::read_many`.
2. **CPU gather telemetry is narrower than its name suggests.** `ggml_sched_independent_cpu_gather()` only accepts a CPU split containing exclusively host-weight `GGML_OP_GET_ROWS` nodes and CPU input IDs. Its counter increments only when a CPU split follows a Meta split and can bypass that intra-graph dependency fence (`ggml/src/ggml-backend.cpp:1860-1914`). `cpu_gathers=0` therefore does not prove GET_ROWS was absent. V20 FIFO totals also report `host_results>0`, so host results were staged. The scheduler does not log which exact predicate rejected independent-gather eligibility.
3. **The frame path is shape-gated.** `llama_context_prefill_frame_batch_ready()` requires a full ubatch, one sequence, contiguous positions, and no embeddings (`src/llama-context.cpp:103-130`). The complete V20 log contains two 3,072-token shape-warmup events, each followed by a 2,048-token shape drain; neither reaches `active` or `replay_ready=1`. The graph input reuse check separately compares recurrent `head` and `rs_z` (`src/llama-graph.cpp`, `llm_graph_input_rs::can_reuse`), but this particular log does not establish that `rs_z` changes on every block. At 8K, `ubatch=3072` provides too few full blocks to demonstrate a stable replay state. `ubatch=1024` provides eight full blocks and is the right shape for the next qualification; keep all recurrent/QSA guards and record each state transition.
4. **3+3 dispatch does not itself make an island pipeline.** `llama_context::graph_compute()` calls `ggml_backend_sched_graph_compute_async()`, which enters `ggml_backend_sched_compute_splits()` and submits the graph's backend splits in graph order. FIFO snapshots and event waits preserve dependencies but do not independently schedule a second layer partition. The V11 timeline confirms no island overlap. A separate bounded frame executor is the path that can submit another frame while the opposite island is consuming the previous frame's activation.


## QSA device-bias/KQ-mask audit (read-only)

- The current V21 run log (`results/20261015T111920Z/server.log`) has `t_inputs` averages of 4.48 ms (`n=64`, token shape 5..3072), 7.36 ms (`n=96`, 36..1024), and 12.90 ms (`n=416`, 20..1024) per `process_ubatch` in 32-call windows. This timer brackets `llm_graph_result::set_inputs()`, so it includes PLE hash IDs, QSA input preparation, and the KQ-mask builder. For an 8K prompt with `ubatch=3072`, three calls at the observed maximum place an approximate upper bound of 39 ms on all host input preparation; QSA alone is smaller. It cannot account for the roughly 9.2 s single-request TTFT/8K PP time.
- `llm_graph_input_qsa::set_input()` calls `set_input_qsa()` once per QSA input object. `qsa_inps` is keyed by compression ratio, so layers sharing a ratio share one input object; the 48-layer model metadata has QSA ratio 4 entries, not one host fill per QSA layer. `llm_graph_input_mem_hybrid_idx` separately fills the KQ mask once per graph input. Both are CPU-side input preparation today.
- For the common causal text path, the graph sets `blk_bias` and stores a block bias of `[ceil(n_kv/4), n_tokens/n_stream, n_stream]` F32 plus the per-cell KQ mask `[n_kv, n_tokens/n_stream, 1, n_stream]` F16. At `n_kv=8192`, total tokens=3072, this is 24 MiB of block bias plus 48 MiB of KQ mask per input set. At `n_kv=65536` with the same token batch, it grows to 192 MiB + 384 MiB. The KQ-mask code copies a full `n_kv` row for each later query in a stream, then recomputes changed cells; the QSA bias code writes one value per block/query. Both costs scale with context length.
- There is no existing CUDA builder for these input tensors in the current QSA CUDA kernel: `qsa-attn.cu` consumes the supplied bias/mask. The archived `multistream-20261010/qsa-candidate` is a different optimization: it feeds explicit physical cell IDs into the existing sparse attention kernel to avoid F16 K/V gathering. It does not move `set_input_qsa()` or `set_input_kq_mask()` to CUDA, and its CUDA fixture was not GPU-validated.
- The backend already exposes the generic public `ggml_backend_reg_get_proc_address()` API and existing versioned private CUDA tables (`ggml_cuda_ft_dense_api_v4`, Meta async-copy, P2P AR). There is no QSA bias/mask proc today. A minimal no-new-enum design is a new versioned private proc table such as `ggml_cuda_qsa_input_api_v1` registered by name, with the CPU path retained as fallback. The interface must enqueue work on the relevant CUDA backend stream and handle every child of a Meta backend; simply changing `bias->data` from CPU fill to a CUDA-side write would race the following H2D/graph execution. Avoid adding a public `GGML_OP_*` enum in `ggml.h`; that header fanout is what triggers broad CUDA recompilation.

## Three highest-value candidates and quantitative bounds

1. **Make the existing two-frame path stay eligible for the whole 8K request.** Use the planned 1,024-token ubatch so there are eight full frames; preserve the recurrent/QSA checks. The V11 interval data provides a strict upper bound of 9,421 ms per four-request prefill window for removing all serialization of the slower island (about 2.36 s per 8K lane if evenly attributed); real gain is lower. V20 must show steady `active`, reused graph, and replay-ready on chunks after the recurrent shape transition before claiming it.
2. **Move CPU PLE row fetch off the serialized per-frame host path.** The V11 timing budget is about 0.89 s per graph call / 28.5 s across the 32 calls in the four-8K wave. That is the maximum possible CPU-side win for that old trace, not a measured pure-GET_ROWS duration. A safe candidate is a double-buffered, exact-row PLE gather/read-ahead using the existing page-batched row reader and explicit ownership until the matching GPU upload event completes. The V20 hybrid placement is already a substantial step; verify its `t_compute`/PLE row-cache counters before proposing a second CPU PLE rewrite.
3. **Treat P2P all-reduce as the largest measured GPU-kernel target, but cap expectations.** Its any-device interval union is 5,889 ms in the V11 window. The direct relay6 fixture measured a benefit only for small payloads around 200 KiB; large segmented collectives use another kernel path, and the compact-stage correctness barrier adds roughly 1–2 ms at 15M floats. Do not extrapolate the small-payload relay result to 1,024-token prefill collectives. A per-size trace/dispatch map should gate any large-payload redesign; even an ideal single-category kernel speedup is bounded by 5.9 s in this old four-request window.

The 6,000 tok/s goal requires an 8K prompt to complete in about 1.37 s. V21 measured 890.19 tok/s for its real-token-pool PP run (~9.2 s per 8K). QSA input construction can save at most tens of milliseconds at this context; frame overlap and PLE host work are the larger paths. Existing evidence does not support claiming 6,000 tok/s is reachable yet. Preserve exact output quality while measuring each candidate.
