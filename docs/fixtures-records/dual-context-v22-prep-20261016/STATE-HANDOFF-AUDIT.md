# State handoff and historical ubatch audit

Read-only source/result audit for the larger-prefill-context → two 2-lane decode-bank design. No core source was changed and no model/GPU was run for this audit.

## `state_seq` contents and compatibility

- `llama_state_seq_get_size/data` and `llama_state_seq_set_data` serialize/restore `llama_context::memory` only; the public wrappers call `synchronize()` first. The state stream starts with a magic value and source sequence ID, but restore passes the requested destination sequence ID into the memory reader. See `src/llama-context.cpp:5550-5612, 6762-6770`.
- `llama_memory_hybrid_idx::state_write` writes attention/recurrent state and then the indexer state. A full restore invalidates QSA pooled-block state and rebuilds indexer slot metadata from the restored attention cells. Pooled block keys themselves are not serialized. See `src/llama-memory-hybrid-idx.cpp:399-445`.
- For DSV4, persistent raw and compressed KV are intentionally per-sequence even if the public unified flag is set: `unified_raw=false` and `unified_compressed=false` (`src/llama-kv-cache-dsv4.cpp:1244-1248, 1290`). The state constructor uses `n_stream = n_seq_max` for these per-sequence caches (`src/llama-kv-cache-dsv4.cpp:907`; `src/llama-kv-cache.cpp:87`). Thus a source context with `n_seq_max=2`, non-unified mode, and only sequence 0 active has persistent `n_stream=2`; a decode context must also have `n_seq_max=2` and the same stream layout.
- Active graph stream width is different from persistent cache stream count. The graph derives stream width from the current ubatch's unique active sequences, so a one-sequence prefill uses one active stream while the cache still owns two per-sequence streams (`src/llama-graph.cpp:51-56, 1633-1639`; DSV4 compressed graph planning at `src/llama-kv-cache-dsv4.cpp:196-203`). Keep `n_seq_max=2`, place the prefill in seq 0 only, and preserve non-unified KV.
- Restore rejects a KV `n_stream` mismatch (`src/llama-kv-cache.cpp:2205-2209`). DSV4 restore also rejects an active cache row count larger than the destination cache (`src/llama-kv-cache-dsv4.cpp:385-400`) and validates stream count, layer IDs, tensor types, compressor ratios/state width, and layer count. Different source/destination capacities are therefore plausible only when the source sequence's actual positions/cells fit the destination per-sequence capacity and all model/cache metadata remains identical. For V22's 8K prompt, the 64K destination is large enough. A prompt longer than 64K cannot be restored into the present per-seq64K target banks; the decode context must itself have enough per-sequence capacity.
- Hybrid recurrent state serializes the selected sequence cells and R/S/P tensors; restore writes them into the destination and resets its rollback index (`src/llama-memory-recurrent.cpp:796-877`). This state is independent of target output buffers and does not substitute for the MTP carry data.

## MTP state that must accompany the cache

- `common_speculative_process()` must run on the full prefill batch before exporting state. It catches the draft context up by feeding each prompt token and the corresponding shifted target `nextn` hidden row, then retains `pending_h` and verification rows. See `common/speculative.cpp:1775-2000`.
- `common_speculative_begin()` only clears deferred/request-local bookkeeping and validates that the draft memory reaches the prompt end; it does not reconstruct MTP's prompt KV (`common/speculative.cpp:1742-1765`). The first `draft()` seeds the next token at `pos0` from `dp.id_last` plus `pending_h`, so the final target argmax and final `nextn` hidden row are required (`common/speculative.cpp:2005 onward`).
- V22 target contexts expose `embeddings_nextn` in unmasked row order. For this mode, `llama_get_embeddings_nextn_ith(-1)` is invalid; use the final prompt row index `prompt_tokens-1` after row restoration (`src/llama-context.cpp:2291-2325`). Carry the target argmax from `llama_get_argmax_ith` and that full hidden vector. The memory state already contains the final prompt token's KV, so the first decode/MTP seed must use the carried next-token argmax at position `prompt_tokens`; do not submit the final prompt token again.
- `common_speculative_get_state/set_state` can serialize MTP's per-sequence `pending_h`, but the current snapshot gate is restrictive: `snapshot_supported()` requires a multi-sequence `seq_layout`, one MTP layer, no chain-head/fold/carry paths, and when GPU multi-chain is enabled it additionally requires `LLAMA_MTP_GPU_CHAIN_MULTI_SNAPSHOT=1` and an inactive chain (`common/speculative.cpp:2755-2804`). The snapshot stores `pending_h` and optional deferred rows, not the full prompt or `verify_h`. If this mode is not supported, the alternate is to sidecar the full prompt's `nextn` rows and rebuild the fresh draft context once; at the cited configuration this is about 320 MiB for 8K tokens. In either design, serialize target and draft memories separately after MTP prefill, and carry prompt token IDs/length and model/runtime identity for bookkeeping.
